# Pip-KeyPet

Виртуальный питомец для **Waveshare ESP32-S3-Touch-AMOLED-1.75C**: эмоции, мини-игры, уведомления iPhone, BLE, QR-визитка и настройки через браузер.

## Прошивка через браузер

**[Открыть веб-прошивальщик](https://666cossack999.github.io/Pip-KeyPet/)**

1. Подключи брелок к компьютеру кабелем USB-C с передачей данных.
2. Открой страницу в **Chrome** или **Edge** на компьютере.
3. Перейди во вкладку **«Прошить / обновить»**, нажми **«Прошить»** и выбери **USB JTAG/serial**.
4. Дождись окончания прошивки, затем открой **«Настройки»**.

Веб-прошивальщик публикуется автоматически из `main` через GitHub Actions. До первого успешного запуска Actions необходимо включить **Settings → Pages → Source: GitHub Actions**.

Для локального запуска панели скачай архив **`pip-keypet-<версия>-panel.zip`** из [Releases](https://github.com/666cossack999/Pip-KeyPet/releases), распакуй его и запусти `Pip-Windows.bat`, `Pip-Mac.command` или `Pip-Linux.sh`. Для прошивки через локальную панель требуется интернет для загрузки esptool-js с CDN (если файл ещё не закеширован браузером).

> **Внимание:** прошивка предназначена только для ESP32-S3-Touch-AMOLED-1.75C. Сохрани важные данные перед экспериментальной прошивкой. Скрипт использует раздельные образы, чтобы не перезаписывать NVS.

## Выбор версии прямо в веб-прошивальщике

На [нашей странице](https://666cossack999.github.io/Pip-KeyPet/) во вкладке **«Прошить / обновить»** можно выбрать:

- **Стабильная (main)** — сборка из последнего успешного запуска GitHub Actions для `main`; выбирается по умолчанию.
- **Тестовая · PR #N** — последняя успешно проверенная сборка **текущего коммита** открытого PR с изменениями `firmware/`, `ui/` или зависимостей сборки из нашего репозитория. Отмечена предупреждением, остаётся доступной до закрытия PR.
- **Файл из GitHub Actions** — скачай артефакт `pip-keypet-firmware`, распакуй и укажи `firmware.js` или `firmware.json` в панели.

Каталог публикуется автоматически в GitHub Pages отдельным workflow `publish-firmware-catalog.yml`, когда завершится успешная сборка прошивки. Не нужно сливать тестовый PR в `main`, создавать тег или GitHub Release, чтобы он появился в списке. В каталог попадают только прошедшие CI образы из PR с изменениями прошивки или UI устройства; устаревший коммит не публикуется. При отсутствии каталога остаются доступными стабильная прошивка и загрузка файла. **Тестовые прошивки используются на свой риск; USB остаётся способом восстановления.** До аппаратных тестов использовать тестовую сборку только на плате, которую можно восстановить.

Выбор прошивки сейчас применяется к USB Web Serial; когда BLE OTA пройдёт аппаратные проверки, его отдельная кнопка сможет использовать тот же выбранный образ.

## Обновление без кабеля (BLE OTA)

После **первой установки по USB** можно обновлять только приложение по Bluetooth.
На ПК используй Chrome/Edge; на iPhone — браузер [Bluefy](https://bluefy.app/), так как Safari не поддерживает Web Bluetooth.
Открой вкладку «Прошить / обновить» и нажми **«Обновить по Bluetooth»**.
Для OTA нужен заряд не менее 50% или питание USB; при сопряжении подтверди код верхней кнопкой.
USB остаётся способом восстановления. См. [подробный протокол и проверки](docs/BLE_OTA.md).

## Релизы

- Каждый push в `main` собирает прошивку; после успешной сборки отдельный Pages workflow публикует страницу с актуальным образом и проверенными PR-превью.
- Тег `vX.Y.Z` запускает сборку и создаёт [GitHub Release](https://github.com/666cossack999/Pip-KeyPet/releases) с бинарниками и архивом панели.
- Версия в теге должна совпадать с `PROJECT_VER` в `firmware/CMakeLists.txt`.
- В pull request собирается только проверочный образ; после успешной CI он включается в общий каталог как тестовая сборка. Официальный релиз не создаётся.

Создать тег релиза после успешной проверки:
```bash
git checkout main
git pull
git tag v1.1.0
git push origin v1.1.0
```

## Синхронизация feature-веток с main

После каждого merge в `main` GitHub Actions **Check feature branches against main**
проверяет открытые PR и помечает отставшие ветки меткой `needs-main-sync`.
Если GitHub подтверждает конфликты, добавляет `main-sync-conflict`.
Та же проверка запускается на изменениях PR, вручную и по будням.
Для PR, переведённых из draft в готовые к слиянию, отставание от main
означает **красную CI-проверку**. Draft PR остаются рабочими и не блокируются.

Обновление ветки выполняется только контролируемо, не автоматически:

```bash
git fetch origin
git switch feature/ble-ota
git merge origin/main
# если есть конфликты — разрешить с сохранением обеих функций,
# проверить веб-панель, симулятор и прошивку
git push origin feature/ble-ota
```

Перед финальным merge в `main` обязательно проверить, что ветка не отстаёт,
сборки зелёные, регрессий нет, а изменения в ESP32 протестированы на железе.
После успешного merge исходная feature-ветка удаляется автоматически.

**Важно:** при объединении BLE OTA, «Найти Пипа» и обновления веб-панели
сохранять обе функции; при конфликте версий согласовать `PROJECT_VER`,
не применять `ours/theirs` ко всем файлам и не переписывать опубликованную историю.

## ES7210 — исправление перезагрузки 1.75C (тестовая версия)

На реальной плате с прошивкой `1.1.0` обнаружен boot loop:
`ES7210: Open fail` → `assert failed: bsp_audio_codec_microphone_init`.
Сканирование общей I²C-шины показало `0x18, 0x34, 0x41, 0x5A, 0x6B`.
Управляющий адрес ES7210 на этой плате — вероятно, **0x41**, тогда как
BSP Waveshare 3.0.0 пытается использовать **0x40** (`0x80` в 8-битном
формате драйвера).

Для тестового образа `1.1.1-micfix-rc1`:
- `tools/patch-es7210-address.py` после `idf.py reconfigure` корректирует
  *проверенное определение* адреса в загруженном компоненте BSP: пробует
  `0x41` и `0x40`, а драйверу передаёт `0x82` или `0x80` соответственно;
- `mic_task()` до вызова библиотеки проверяет наличие хотя бы одного из этих
  адресов. Если устройство физически не отвечает, Пип загружается без
  микрофона вместо бесконечных перезапусков;
- настройки и сохранения не очищаются; команда `erase_flash` не нужна.

**Пока это экспериментальный hotfix.** Перед слиянием в `main` требуется
подтвердить на устройстве, что ES7210 обнаружен, запись регистра проходит,
микрофон работает и пропал boot loop. CI проверяет исходный код и сборку,
но не электрическое подключение I²C. Для локальной сборки используй
`tools/release.sh`, а не голый `idf.py build`: скрипт применяет исправление BSP.

## Разработка

```bash
git submodule update --init --recursive
# Требуется ESP-IDF 5.5
tools/release.sh
python3 tools/package-release.py
```

Исходники прошивки — `firmware/`; интерфейс — `ui/`; веб-панель — `docs/`; инструменты — `tools/`.
